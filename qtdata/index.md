# 量潮数据

量潮数据为高校科研团队与高新科技企业提供数据处理服务：把原始数据变成可靠、可直接使用的结构化数据。数据条目平均在 100 万以上、最大数十亿，数据量平均在 50 GB 以上、最大 10 TB。交付遵循科研领域的可复现标准，附带完整处理日志，供论文评审时溯源。

这条业务线的工作按数据从原料到成品的三个阶段组织——**采集、清洗、大模型挖掘**。下面是我们在这三个阶段里的主要案例。

## 采集

把散在互联网和客户系统里的原始数据完整、稳定地拿下来。

**高频电商价格采集**。源于量潮科技前身——厦门大学 China's Prices Project（CPP）课题组十年的积累：每天采集天猫和京东平台 1000 余个关键词、约 500 万数据点，编制中国高频线上价格指数。CPP 期间经历了从个人电脑定时爬虫到腾讯云服务器集群、从 13 人手动维护到自动化系统的演进，也留下了爬虫第 23 版、小文件 CSV 存储困境、MongoDB 方案设计这些具体经验。十年后这套系统以对象存储、ClickHouse、Python 自动化流水线重新实现，指数按日构建、列式查询、可视化输出。

承接采集类需求时，反爬虫强度是报价前必须评估的一项——它直接决定工时与风险。

## 清洗

把散在不同系统、不同格式里的数据弄干净、对齐，合并成一张能分析的表。

**制衣厂生产效率数据合并**（某高校研究者与服装制造厂合作的研究项目）。客户的原始数据来自四个互不相通的地方——几百份工人与班组长的纸质问卷、产量表（谁、哪天、哪道工序、完成多少件）、工序表（每个款式的标准工序、机器、标准时间）、返工与考勤记录。我们的工作分两层：

- **数据侧**：把四个来源按**款号、日期、员工**三个维度合并成统一分析集，用于员工绩效计算、款式生产效率分析、返工率影响评估与成本核算。合并的依据是制造业的产值公式 `产值 = 员工 × 工序 × 产量`（产量还要带返工率）。
- **人填数据的清理**：问卷这一侧的问题不在题目设计，在填和录入——收入栏有人多打一个 0、有人少打一个 0；量表题有正向计分与反向计分混在一起（不区分就加总分，结论会反过来）；还有整份乱填、大片空白的低质量答卷，得先和研究者商定「哪些整体剔除、哪些保留部分缺失」的标准再动手。

这类项目里，**沟通与设计占大头**：数据来自不同系统，匹配逻辑复杂且依赖经验，要先把数据来源、初始质量、清洗预期和客户一条条对齐，才敢下手。交付物是能直接进入分析的干净数据集。

## 大模型挖掘

把非结构化的文本，用大模型变成结构化的、能统计的信息。这一类需求近年增长很快，常常是企业要做 AI 应用的前置工作。

**电商评论挖掘**。客户想知道某个品类的消费者评价集中在哪些维度（例如制冰机：制冰速度、冰块大小）。我们采集评论数据后，用大模型做两遍处理：第一遍把每条评论里相关的信息摘成一小句一小句，第二遍再做归类和总结，输出消费者关注的评价维度及其分布。

这一类交付的质量标准是**分类抽检的准确度**：准确度要求越高，算法调优和细化的工作量越大，费用非线性增长——所以开工前要先和客户把准确度目标谈定。

**面向企业研发的结构化语料**。生物科技等高新科技企业需要从大规模非结构化数据中提取结构化信息，用于构建知识库或模型训练。这里的工程难点不在单条数据的处理（对现在的大模型来说，单个环节难度不高），而在**把整条流水线组装起来**——这非常考验数据工程团队的习惯。相应地，需要大模型 API 调用的标注类工作，费用中单列 API 调用成本。

## 这一类业务的难点

订单规模不大（多为数千元到一两万）、周期短（几周结项）、客户对质量要求高。真正的难点不在单个技术点，而在**保持经营效率、减少隐形摩擦**——需求要说清、报价要透明、过程要跟得住。这也是量潮数据持续把隐式经验写成显式文档、再转成代码的原因。
